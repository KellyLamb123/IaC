# Лабораторная работа №1 — Ansible

## 1. Разработка роли без использования сторонних ролей

В этой лабе я собирал роль opensearch для установки OpenSearch и OpenSearch Dashboards 3.8.0. Работал в репозитории IaC, в ветке lab-1. Разделил логику на установку, настройку и проверки. Использовал стандартные модули Ansible apt, command, assert и uri. Решил не изобретать велосипед со своими скриптами на каждый чих.

На скриншотах есть структура роли и фрагменты её кода. Полных исходников в архиве нет. Поэтому проверить отсутствие сторонних ролей только по этому архиву нельзя. Репозиторий и рабочая ветка показаны на скриншоте 2.

## 2. Установка непосредственно на Linux-машину

Стенд поднял через Multipass. Создал виртуалку iac-lab1 с Ubuntu 24.04. Выделил два ядра, четыре гига оперативки и двадцать гигов диска. Выполнил multipass launch 24.04 --name iac-lab1 --cpus 2 --memory 4G --disk 20G. Потом проверил машину через multipass list и multipass info iac-lab1. Виртуалка запустилась и получила адрес 192.168.252.2. Внутри стояла Ubuntu 24.04.5 LTS с архитектурой aarch64 и systemd 255. Создание и проверка ВМ показаны на скриншоте 3 и скриншоте 4.

![Скриншот 4. Проверка окружения Ubuntu](screenshots_lr1/4.png)

Ansible запускал со своего Mac. Пакеты ставил прямо в Ubuntu через apt, без Docker и контейнеров. Сначала проверил SSH-подключение модулем ping. Использовал пользователя ubuntu и свой SSH-ключ. После настройки inventory выполнил ansible opensearch -m ping. Хост opensearch-node вернул pong. Коннект есть, можно катить дальше. Это видно на скриншоте 5 и скриншоте 7.

## 3. Стандартные директории роли

Роль разместил в roles/opensearch. В defaults вынес настройки по умолчанию. В files положил файлы пакетных репозиториев, а в templates — шаблоны конфигов. Задачи разместил в tasks. Разделил их на подготовку репозитория и системы, установку, настройку и проверки. Так проще найти нужную таску. Не приходится искать её к чёрту на куличики внутри огромного файла.

В структуре также есть handlers, meta, tests и vars. По заданию эти папки должны содержать полезные файлы. Просто создать пустые директории недостаточно. На скриншотах не видно содержимого meta, tests и vars. Код handlers тоже не показан. Эту часть ещё нужно проверить по исходникам. Структура и список файлов показаны на скриншоте 6 и скриншоте 9.

## 4. Установка заданной версии, настройка системы и запуск

Версию OpenSearch зафиксировал на 3.8.0. Передал её в задачу установки через модуль apt. Затем добавил проверку через dpkg-query. Полученную версию сравнивал с нужной через assert. Так сразу понятно, какой пакет установился. Ещё подготовил файлы репозиториев обоих продуктов и шаблон системной настройки vm.max_map_count. Для неё задал значение 262144. Задача установки и проверка версии показаны на скриншоте 11.

![Скриншот 11. Установка и проверка версии OpenSearch](screenshots_lr1/11.png)

Для OpenSearch выбрал режим single-node. Security-плагин в учебном конфиге отключил. После настройки сервис запускался через роль. Проверки подтвердили установку OpenSearch и Dashboards версии 3.8.0. Полный список зависимостей на скриншотах не виден. Применение системного параметра отдельно тоже не показано. Эти моменты ещё нужно сверить с задачами роли.

## 5. Параметризация роли и значения по умолчанию

Основные настройки вынес в defaults. Так можно менять стенд без правок тасок и шаблонов. Параметр opensearch_version задаёт версию. По умолчанию это 3.8.0. В opensearch_cluster_name указал имя opensearch-lab. Параметр opensearch_node_name берёт имя хоста из inventory. Фиксированная версия нужна для повторяемого деплоя. Имена можно менять под своё окружение. Для opensearch_network_host задал 127.0.0.1, а для opensearch_http_port — 9200. В таком сетапе API OpenSearch слушает локальный интерфейс виртуалки.

Для opensearch_dashboards_host указал 0.0.0.0. Так Dashboards слушает все сетевые интерфейсы ВМ. Порт вынес в opensearch_dashboards_port со значением 5601. В opensearch_vm_max_map_count записал 262144. За ожидание готовности отвечают opensearch_readiness_retries и opensearch_readiness_delay. Задал двенадцать повторных попыток и паузу пять секунд. Время ожидания можно подстроить под скорость машины. Не нужно хардкодить его в каждой проверке. Значения показаны на скриншоте 8.

## 6. Конфигурационные файлы через Jinja2

Конфиги оформил через шаблоны Jinja2. Ansible подставляет в них значения переменных. В шаблон OpenSearch добавил имя кластера и ноды, пути к данным и логам. Туда же вынес адрес и HTTP-порт. Режим single-node и отключение Security-плагина задал прямо в шаблоне. Он показан на скриншоте 12.

![Скриншот 12. Шаблон конфигурации OpenSearch](screenshots_lr1/12.png)

Отдельно подготовил шаблоны для Dashboards и системной настройки. Теперь конфиги хранятся вместе с ролью. Их не приходится каждый раз вручную копипастить на виртуалку. Задачи применения шаблонов OpenSearch и Dashboards завершились успешно.

## 7. Применение изменений через handlers

Для обработчиков в проекте есть папка handlers. В выводе запусков видны этапы применения ожидающих обработчиков OpenSearch и Dashboards. Они нужны для перезапуска после изменения настроек. Дёргать сервис без причины не хочется.

Повторный прогон прошёл без изменений. Счётчик changed остался нулевым. Но код handlers и вызовы через notify на скриншотах не показаны. Отдельной проверки с изменением конфига тоже нет. Поэтому эту часть ещё нужно проверить по исходникам. Затем стоит поменять настройку и проверить срабатывание нужного обработчика.

## 8. Автоматический запуск после перезагрузки

После настройки проверил состояние OpenSearch через Ansible и systemctl. Выполнил ansible opensearch -b -m command -a "systemctl is-active opensearch". Затем запустил ansible opensearch -b -m command -a "systemctl is-enabled opensearch". Получил active и enabled. Сервис работает и включён в автозагрузку. Результат показан на скриншоте 14.

![Скриншот 14. Результаты запуска OpenSearch и проверка автозагрузки](screenshots_lr1/14.png)

Модуль command вывел CHANGED для этих вызовов. Но сами команды только читали состояние сервиса. Настройки они не меняли. Ответ enabled подтвердил включённую автозагрузку. Перезагрузка ВМ с повторной проверкой на скриншотах не показана.

## 9. Проверка готовности OpenSearch через API

Добавил ожидание готовности через модуль uri. Без него проверка сразу после старта могла бы отработать через пень колоду. Модуль обращается к API состояния кластера. Ожидает HTTP 200 и статус green или yellow. Число повторных попыток ограничено настройкой роли. Между ними есть пауза. Потом отдельным запросом получаю информацию OpenSearch. Сверяю версию и имя кластера. Логика показана на скриншоте 13.

![Скриншот 13. Проверка готовности через API](screenshots_lr1/13.png)

Проверка завершилась успешно. OpenSearch 3.8.0 готов и настроен правильно. Для Dashboards тоже прошли ожидание API и проверка версии. Значит, оба сервиса отвечают на запросы.

После настройки отдельно проверил состояние кластера через REST API OpenSearch. Для этого выполнил команду:

```bash
multipass exec iac-lab1 -- curl -sS 'http://127.0.0.1:9200/_cluster/health?pretty'
```

В ответ получил JSON со статусом green. Кластер opensearch-lab работает в режиме single-node, количество узлов — 1. Все 12 шардов активны, неназначенных шардов нет, задач в очереди тоже нет. Значит, OpenSearch нормально поднялся, API отвечает и с распределением шардов всё в порядке.

Результат проверки показан на скриншоте 16.

## 10. Окружение, команды запуска и итог проверки

Работал на Mac с macOS 26.6.2 и архитектурой arm64. Использовал Ansible Core 2.21.4 и Python 3.14.7. В качестве удалённой машины поднял Ubuntu 24.04 через Multipass. Окружение проверил командами `sw_vers`, `uname -m` и `ansible --version`. Перед деплоем проверил синтаксис через `ansible-playbook --syntax-check playbook.yml`, затем запустил сам плейбук. В процессе столкнулся с ошибкой SSH `Permission denied (publickey)`. Пришлось поправить права доступа к приватному ключу и добавить его в `ssh-agent`, после чего подключение заработало. Также были предупреждения Ansible, но на выполнение задач они не повлияли.

![Скриншот 1. Окружение управляющей машины](screenshots_lr1/1.png)

![Скриншот 10. Проверка синтаксиса и запуск](screenshots_lr1/10.png)

После настройки OpenSearch и Dashboards проверил работоспособность сервисов через API. Оба успешно запустились, версия 3.8.0 подтвердилась. Дополнительно выполнил `GET /_cluster/health`, получил статус `green`, один работающий узел и 12 активных шардов без ошибок. Затем повторно запустил плейбук командой `ansible-playbook -i inventory.ini playbook.yml`. Получил `ok=29`, `changed=0`, `unreachable=0`, `failed=0`, `skipped=3`. То есть Ansible не стал по новой накатывать уже существующие настройки. Идемпотентность работает как надо, лишних перезапусков не произошло. Лог повторного запуска сохранил в `artifacts/lab1/repeat.log`. В итоге роль успешно устанавливает, настраивает и проверяет OpenSearch и Dashboards в режиме single-node без использования Docker.
